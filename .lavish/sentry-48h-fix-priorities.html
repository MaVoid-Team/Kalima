Kalima · Sentry triage · last 48 hours

Make the live viewer resilient and keep local failures out of production triage.

Live reproduction confirmed a third-party PDF fullscreen failure. The apparent account errors were emitted by localhost development sessions, while the e-booklet editor timeout happened during slow post-upload preview generation.

Recommended focus: remove the incompatible fullscreen action, return version creation before background preview work can time out, and stop development telemetry from polluting the production Sentry project.

Proposed order of work

P0 · first

Remove PDF fullscreen where it is not reliable

The external PDF viewer calls the browser fullscreen API without its own compatibility guard. Disable that menu action in the protected sample viewer, while retaining normal document viewing, zoom, paging, and download.

Result: unsupported Android webviews no longer throw an unhandled error.

P1 · next

Return e-booklet version creation before preview rendering

Creating a version currently waits for page-preview preparation. Make preview preparation best-effort background work so large documents cannot hold the HTTP request open until the reverse proxy gives up.

Result: admins receive a successful version-creation response instead of a 504.

P1 · next

Make delivery failures clear and non-noisy

Validate delivery requirements in the form before sending the request and surface the backend reason inline. Preserve the existing server-side validation and never change an order when the request is incomplete.

Result: admins know what to correct without an unhandled Sentry error.

P2 · after

Keep noise out of the production issue list

Ignore the known benign resize-observer browser warning and remove hard-coded Sentry DSN fallbacks. Local development errors will no longer be sent to the production project by default.

Result: Sentry reflects actionable production failures.

Delivery sequence

Reproduce the account and admin paths in production-like conditions. Confirm the exact failure point before changing behavior.
Ship the account-access repair with focused tests. Cover login, refresh, and student registration under a busy database.
Ship fullscreen graceful fallback and admin recovery separately. These are contained changes with lower customer impact.
Verify the live journeys and watch Sentry for 48 hours. Resolve only the reports that stop recurring after the release.

What I would not prioritize yet

The single unexplained browser report should be instrumented, not guessed at. The port-conflict report is also lower priority unless it reappears in production, because it commonly comes from a duplicate local or deploy process rather than a customer journey.
